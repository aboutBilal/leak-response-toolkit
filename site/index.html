If a secret has leaked

The first 15 minutes

  1. 0–2 min

    Say it out loud. Tell your lead or security channel, then start the record: a UTC timeline, with the read-only steps below run in order.

    leak respond owner/repo
  2. 2–5 min

    Keep the evidence. If the copy is yours and public by mistake, make it private. Don't delete it yet.

    leak snapshot owner/repo
  3. 5–10 min

    Rotate the most powerful secret first. Revoke the old value; adding a new one is not enough.

    leak rotate aws-key
  4. 10–15 min

    Scan the whole history for every other secret, then put them in order.

    leak scan ./repo && leak plan
  5. Then

    Remove copies, check the logs, notify.

    leak hunt owner/repo

      - id: leak-guard            # also scans staged changes with gitleaks

Questions teams ask first

Does it send my code or secrets anywhere?
No. scan, audit and plan run entirely on your machine, and rotate uses your own cloud CLI, or the GitLab API, only for the steps you apply. hunt and audit-org send only repository names, account names and commit IDs to public services.
Why doesn't it test whether a leaked key still works?
Using a leaked credential is what an attacker does, and it can trigger alarms or break a provider's terms. The answer is the same either way: rotate it.
Does it work outside GitHub?
Yes. Scanning, auditing, the hooks and the CI templates work with any Git repository on GitHub, GitLab, Azure DevOps or Bitbucket, and audit-org grades whole organisations on all four.
How does it compare with gitleaks or TruffleHog?
Detection comes from gitleaks. The toolkit adds grading, rotation plans and guided rotation, runbooks, the hunt for copies and the leadership report. See the comparison.
Can my company use and change it?
Yes. It is MIT-licensed. Adapt the runbooks to your organisation and ship the prevention kit in your repository templates.
Where do I get help?
Ask in Discussions. Report vulnerabilities privately, as described in the security policy.
